# 结构哨兵实验对照

以下保留迁移前的历史测量及后续优化记录。结构哨兵方案已整合进 `source_map.lua`，
旧编辑快路径、独立实验原型及其对照脚本均已删除，历史测量不再提供原脚本复现入口。
当前实现的回归验证见 `tests/sentinel_structure_cache.lua`、`tests/source_map_incremental.lua`
和 `tests/source_map_tags.lua`；当前解析基准见 [标签收集器对照](layout-query-benchmark.md)。

## 对照方式

- 环境：Neovim 0.12.6、chezmoi 2.73.1，使用独立临时配置、data 和 include 文件。
- 旧版：实际 `diff.trace.update_static`，失败才调用 `sentinel.trace`，不是每次强制完整渲染。
- `active buffer` 使用真实 buffer 和局部字节编辑，让旧版使用增量 Tree-sitter parser；新版 demo 仍用 string parser。
- 两版使用相同模板、配置与编辑序列，每次输出都与普通 `execute-template` 的参考结果比较。
- 初始渲染、参考输出和 buffer 写入不计时；计入解析、映射、输出重建和必要的外部进程。不含 debounce、hunk diff、UI 或异步调度。
- 冷渲染每组 6 次，其他组 12 次，表中为单次耗时中位数。普通编辑组在两个版本间交替，首个样本与已初始化文本相同，后面有 11 次真正修改。
- 示例数字来自一次本机运行，不是跨机器性能保证。脚本还输出 p95、总耗时、进程数及缓存命中数。

## 迁移后的实现

首次迁移为兼容保留了 segments、静态节点边界及空 gap 执行锚点；segments 现已移除，
后面的“统一静态槽位”小节记录了当前实现。
所有静态修改统一从结构结果恢复；保留异步进程、120ms debounce 与过期刷新丢弃机制。
最近一次全文相同直接返回完整 trace，结构历史最多保存 32 个结果。
`cli.invalidate()`、watcher 和公开 `api.invalidate_cache()` 都会清除渲染缓存；
失效前启动的异步请求不能重新填充新一代缓存。

缓存现已统一由 CLI 管理：`execute_template(..., { cache = true })` 显式启用最多
32 条模板输入/结果缓存，普通执行仍默认不缓存。sentinel 只保留最近一次完整 trace，
通过 `cli.context_generation` 判断 trace 和重建结果是否仍有效，不再维护骨架缓存或
独立的 invalidate 接口；CLI 也不再反向依赖 sentinel。buffer 的语法缓存保持独立。
失效范围可选 `all`（默认）、`paths`、`data` 和 `templates`；data 失效会连带清空模板。
watcher 对已发现的 `.chezmoitemplates` 及其子目录使用 templates 范围失效，使
`includeTemplate` 修改后的下一次渲染不再复用旧输出，同时保留路径和 data。

同时修复了下述重复前缀扫描瓶颈：layout 先建立行首索引，再二分换算位置。
`tests/sentinel_structure_cache.lua` 在生产实现上检查 426 次输出和 source-map 范围，
其中 378 次静态编辑不启动外部进程，另外覆盖全文缓存、init 隔离、无末尾换行和异步失效。
一次迁移后复测中，5.3KB/100 if 的 buffer 静态更新中位数约 1.2ms，
21.2KB/400 if 约 4.4ms；后者循环体、未执行分支、空块、trim 和多处修改约 4.5–5.3ms，
均未启动外部进程。全文未变的快路径低于 0.01ms。
单独 layout 约 8.7ms，其中行列换算约 0.39ms；结构变化时仍可能先尝试重建再解析一次，
这条低频路径尚未做进一步合并。
下面的旧版耗时与瓶颈说明保持为历史记录，不代表优化后的性能。

### 后续：单遍与局部 layout

`lua/vimoi/gotmpl/source_map.lua` 现在通过兄弟分隔符直接收集完整标签，缓存 buffer 的原始
标签范围；字面文本由相邻标签的间隙推导。
`on_changedtree` 提供语法变化范围，`on_bytes` 补充不改变树形的文本变化，并移动已有
脏区；布局刷新时只遍历这些区域及必要的相邻完整节点。多处编辑保持独立范围，
新片段与未变化的旧片段线性合并，不再全量排序。没有依赖跨树的 node ID。

初次加载、没有 buffer 的字符串输入，以及语法错误后的恢复会全量收集。缓存随 parser
detach 释放，不受 data/config 变化影响。旧 trace 不会被缓存更新原地修改。

按 80 次局部编辑的平均值，21KB/400 if 样例的 layout 从约 4.43ms 降至 0.83ms，
其中语法更新与缓存维护约 0.26ms，导出平面映射约 0.57ms。同长度替换与增删文本接近。
5.3KB/100 if 样例约 0.23ms。这里只测 layout，不包含渲染、diff、debounce 或 UI。
现有 diff/merge 仍要求完整的绝对位置数组，所以导出、偏移移动并未变成严格的局部工作。

运行 `tests/source_map_incremental.lua` 可将增量结果逐次与全新解析对照：703 组覆盖
trim、增删嵌套块、裸括号节点拆分/合并、临时语法错误、连续编辑、undo/redo。
400 if 的样例收集节点数为全量 4002，尾部局部编辑 2，相隔两处编辑 4。
这里统计递归收集器访问次数，不包含二分定位时的节点探测。

### 后续：统一静态槽位

`literal_parts` 已包含完整的源范围、执行次数及各次输出范围，可以覆盖原 segment 的映射用途。
现在投影、merge 和滚动统一使用字面文本；`output_ranges` 中的范围使用 `start_byte`/`end_byte`，同一
输出位置的空槽位按哨兵执行顺序排序。空槽位仍保留，真正的控制块边界仍可交互选择。

移除了 segment 类型、文本节点布局、未使用的行列/文本/trim 字段、槽位到节点的二次
映射，以及重复的 trim 计算。语法缓存只收集 action 分隔符，静态槽位从相邻边界推导。
裸 `{` 的 parser 节点边界不再导致选择；独立 action 两侧的同字节候选仍保持选择。
同样的 21KB/400 if 样例，100 次局部修改平均 layout 约 0.40ms，完整 trace 重建约
0.71ms（不包含 diff/UI）。layout 与 sentinel 两个模块合计从 575 行减为 514 行。

当前字段命名为 `template_tags`（完整的 `{{ ... }}` 标签）、`literal_parts`（标签之间的
字面文本，包含空文本）和 `output_ranges`（各次执行产生的输出范围）。历史名称
`actions`、`gaps`、`rendered` 已不再作为这些字段使用。

## 能力差异

两版的普通表达式、trim、条件、循环、break/continue、非空 define/block、变量、转义括号和 include 共 18 个基础用例输出相同。当时的独立原型实验验证了新版的 424 次输出，其中 378 次静态文本编辑直接复用结构缓存。

旧版的编辑快路径目前只允许一个执行恰好一次的非空静态文本节点变化，且节点边界和 trim 计数必须满足约束。循环体、未执行分支、空文本与非空文本切换、改变 trim 空白、多处文本同时变化，在此路径会退回完整渲染。

新版对上述修改都能复用相同骨架。每次重新解析当前文本，得到当前 trim 后的文本与位置，再按缓存的骨架输出重建结果与映射，不需要逐个判断文本编辑是否符合旧快路径约束。真正的新 action 仍需要渲染；切回以前渲染过的结构则可命中缓存。

这不是旧哨兵信息不足：旧版已经记录空隙锚点，`predict_literal_edit` 也能推算一些重复/未执行文本修改，但它只返回输出，并不是当前编辑刷新使用的完整 trace 更新路径。上述区别是现有实现之间的区别。

新版目前只完成实验性的输出和 gap 范围，没有生产 trace 的完整 segments/字段格式，也没有接入异步刷新、diff 和 merge。以下时间不能视为完整产品功能等价后的端到端性能对照。新版还会保存多个骨架，demo 没有限制缓存大小。

## 实测时间

5.3KB 样例含 100 个 if；21.2KB 样例含 400 个 if，属于节点密集型输入。

| 场景 | 旧版 5.3KB | 新版 5.3KB | 旧版 21.2KB | 新版 21.2KB |
| --- | ---: | ---: | ---: | ---: |
| 冷渲染 | 27.4ms | 22.2ms | 93.8ms | 85.3ms |
| 单处活动文本，旧版用 buffer parser | 5.7ms | 5.1ms | 73.1ms | 68.2ms |
| 循环体文本 | 23.1ms | 6.0ms | 92.5ms | 68.5ms |
| 未执行分支文本 | 23.1ms | 5.5ms | 92.0ms | 71.4ms |
| 空块插入/删除文本 | 28.8ms | 5.2ms | 94.0ms | 68.1ms |
| trim 边界空白变化 | 25.8ms | 5.2ms | 92.5ms | 68.4ms |
| 同时改两处文本 | 27.0ms | 5.4ms | 91.3ms | 68.2ms |
| 原文本不变再次调用 | 0.005ms | 5.1ms | 0.030ms | 70.0ms |

循环体、未执行分支、空块、trim 边界、多处文本组：11 次真正修改中，旧版启动 11 次进程，新版 0 次。切换两个已知结构：旧版 11 次，新版 1 次。每次修改都产生全新结构时，两版都启动 11 次进程，5.3KB 中位数分别约 22.2ms / 21.0ms，没有明显结构缓存收益。

约 22.5KB、绝大部分为普通文本、仅一个 if 的对照样例：旧版 0.48ms，新版 0.61ms。不能只按文件大小判断性能，也不能说新版在普通文本编辑上一定更快。

## 共同的 layout 瓶颈

21.2KB 样例单独运行 `sentinel.layout` 约 81.8ms，其中 1602 次 `util.byte_to_position` 合计约 70.7ms。该函数每次扫描源文件前缀，节点多时会产生接近二次方的开销。新版 demo 为复用现有解析器，也构造了实际不使用的旧 segments，因此同样受到影响。

这不是 chezmoi 的渲染耗时，也不主要是 Tree-sitter 解析本身。后续可先构造行首索引，避免重复前缀扫描，或者让结构解析仅返回 action 与 gap；还应保留“源文本未变则直接返回”的快路径。此次只测量，没有修改生产代码。

## data/include 失效

两版都不能仅凭模板文本判断外部上下文是否变化。实验先渲染，再修改 config data 与 include 文件，然后只编辑模板末尾静态文本：两版都返回旧动态结果。

旧版重新完整渲染可以刷新结果；新版需要先清空结构缓存。旧版快路径失败时可能顺便刷新，新版会更长期地复用结果，因此不能把这种偶然刷新当成旧版的一致性保证。结构缓存应受显式 invalidate/相关 watcher 管理，不能直接当作永远有效的 CLI 命令缓存。

## 纯空白 define/block

不是普通空白或 trim 不能处理，而是 Go 在定义模板时会区分“只有空白/注释的空定义”和“非空定义”。[Go 文档](https://pkg.go.dev/text/template#Template.Parse)说明空定义不会替换已有定义。

```gotmpl
{{ define "hook" }}original{{ end }}
{{ define "hook" }} {{ end }}
{{ template "hook" . }}
```

去掉示例中的排版换行，原模板输出 `original`，第二个空白定义被忽略。插入非空哨兵后，第二个定义变成真正的非空定义，普通渲染阶段就报 `multiple definition of template "hook"`。事后把哨兵换回空白已经来不及。

空 `block` 默认定义再被非空 define 覆盖也有同样问题。实测旧版和新版都会失败，并非新版新增的退化；普通空 if/循环并不属于这个限制。若支持该特例，骨架预处理/缓存键需要考虑定义体的空性，不能假设所有静态文本变化都完全不影响定义语义。
